# HSG6 online protocol: reverse-engineering reference

Hot Shots Golf: World Invitational (US PS3 digital release **NPUA80864 v01.03**; NP communication
id NPWR03015) spoke to three kinds of Sony Japan (SCEJ) services. This document describes what
was reversed from the game's EBOOT, with enough detail to rebuild the replacement server. Addresses
are virtual addresses in the decrypted `EBOOT.elf` (v01.03, PPU hash
`cdf4e1c581ae975cd6943427043cd527da6937a4`). TOC base for game code is `0xd7e248` (second TOC
`0xd8e1d8` for the network-manager code, `0xd9e050` for the SCE-RT library).

Status markers: **✔** verified in game, **~** implemented but only partly verified, **?** unknown.

---

## 0. Overview

```
             (RPCS3 patch + IP swap: cmnap.scej-online.jp -> server)
  PS3 game ──HTTP :18000──►  hsg6_http.py
     │         GET  /hsg6ps3/ss.info                 bootstrap config (§1)
     │         POST /hsg6ps3/gameapi/<name>          ranking / tournament API (§2)
     │         POST /hsg6ps3/real/mg5_*.cgi          "real" API: app data, server time (§3)
     │         GET  /hsg6ps3/real/files/appdata.xb   FB archive of CSV/text tables (§4)
     │
     ├──TCP :10075──► MUIS  (Medius universe info)     ┐
     ├──TCP :10079──► MAS   (Medius authentication)    │ Horizon, §5
     ├──TCP :10078──► MLS   (Medius lobby)             │
     ├──TCP :10073 / UDP :50000──► DME (lobby world)   │
     └──UDP :10070──► NAT                              ┘
```

Order on "go online": `ss.info` → geteula → login → getservertime → getinfo → signboards →
`mg5_get_event_data` → `mg5_get_app_data` (+ GET appdata.xb) → `mg5_get_server_time` →
getboardlist → getregulationdata → getscorelist ×N → getfinishboardlist → … Medius connects
when the player enters the online lobby menu.

Errors are shown as `%c-%s` with the category letter from `"PSGTRAB"`: **G** = Medius/connection,
**T** = real API (`T-<status hex>`), **R** = game API (`R<request type>-…`).

## 1. Bootstrap: `ss.info` ✔

`GET http://cmnap.scej-online.jp:18000/hsg6ps3/ss.info` (the original URL is
`https://…:18443/…`; the RPCS3 patch rewrites the string at `0xbfd8c0`).

The body is **base64** of a flat list of `<key>value</key>` elements (parser `0x52bdec`, element
reader `0x7f9b94`). No characters may appear between elements; even trailing spaces broke parsing.
`msg1` and `gameurl1` are parsed a second time as nested element lists.

| key | value used | notes |
|---|---|---|
| `ss` | `0` | non-zero = maintenance (shows `msg1`) |
| `msg1` | `<lang0>…</lang0>…<lang19>…</lang19>` | maintenance text per language |
| `daily_ver`, `rank_ver`, `lobby_ver` | `1030` | **must equal 1030** (check at `0x558c34`), else "older version of the game" |
| `scerturl1` / `scertport1` | Medius MUIS host / `10075` | |
| `gameurl1` | `<gameapi_login>URL</gameapi_login>…` | 12 entries: login, geteula, getinfo, getboardlist, getscorelist, regscore, uploaddata, getservertime, getregulationdata, getfinishboardlist, getsignboardlist, getsignboarddetail |
| `realurl1` | `http://…:18000/hsg6ps3/real/` | the game appends `mg5_*.cgi` |
| `interval1` | `60` | min seconds between direct score uploads (`0x5252e0`) |
| `registscore_limithour1` | `24` | |
| `finishboardlist_limitnum1` | `30` | |

Example (decoded): `<ss>0</ss><msg1><lang0>Welcome…</lang0>…</msg1><daily_ver>1030</daily_ver>…`
Generated by `server/make_ssinfo.py`.

## 2. Game API (`/hsg6ps3/gameapi/<name>`) ✔

Source file in the EBOOT: `network_cmnRanking.cpp`. User agent:
`PS3Application libhttp/4.1.1-001 (U-UP9000-NPUA80864_00-EVERYBODYSGOLF06/0000001030)`.

### 2.1 Transport

* **Request:** `POST`, body `p=` + URL-encoded `Blowfish-ECB(K_HTTP, tlv)`. The plaintext is padded to 8
  bytes with `0x04`.
* **Response:** raw `Blowfish-ECB(K_HTTP, tlv)`, zero padded. The client decrypts `floor(len/8)` blocks.
* `K_HTTP = "D9-Zs.2zsB@6"` (`0xd9e340`, set at `0x7f540c`).
* Blowfish is standard with one quirk: **key bytes are sign-extended** (`extsb`) during key
  scheduling, so key bytes ≥ 0x80 differ from textbook Blowfish. Both keys here are ASCII, so it
  doesn't matter for them. The P-array/S-box init tables are in `server/bf_tables.bin`
  (standard pi tables).

### 2.2 TLV

```
element = u16le tag | u16le size_in_4byte_words (INCLUDING the 4-byte header) | data (padded to 4)
```
Integers are little-endian u32. Strings are NUL-terminated and padded. A size of 1 means an empty element.

Every message is an **envelope**:
```
8000 {}                       begin
0000 {u32 result}             reply only: 1 = OK (2/3 = "nothing new" for geteula)
0060 {token}                  session token (see 2.3); optional in requests
...body...
8010 {}                       end
```
Common request elements: `0010` = product code `"NPUA80864"`, `0050` = u32 (2), `0020` = player
online id + `#`, e.g. `"Ninetime#"`.

Example: login reply
```
TLV       00800100 00000200 01000000 20200200 01000000 21200200 00000000 10800100
          8000{}   0000{1}           2020{1}           2021{0}           8010{}
encrypted 3d03453e71d7e4fc7b0425f76df5bfd0d9dcb33c19e88127b92a35482265ed88
```
Example: geteula request (before encryption)
```
00800100 10000400 4e505541 38303836 34000000 50000200 02000000 50100200 00000000 10800100
8000{}   0010{"NPUA80864"}                   0050{2}           1050{0}           8010{}
```

### 2.3 Session token (0x0060)

Blowfish-ECB with `K_SESSION = "l.2F5@B@w@E@26"` (`0xd9e350`) over a NUL-terminated string
containing `_`. The client keeps the part from `_` on. The server never validates tokens; it
mints a random one per reply.

senders at `0x53cfc8`, parsers at `0x53d4e4`. Each parser posts menu event `base` (success) or
`base+1` (failure) via `0x524a14`; menu `OnEvent` table `0x55a828` (index = event − 0xc8).

### 2.5 Endpoints

**geteula** ✔ request `1050` = the agreement version the player already accepted (0 = never).
Reply when versions match: `result=2`, no body (the agreement is skipped). Otherwise:
`1050 {u32 version} 1000 {} 1010 {md5(text)} 1030 {u32 len} 1020 {text\0}`. The client checks the MD5.
The accepted version is saved at `global+0xb869c`. The agreement boxes don't wrap text.

**login** ✔ `2020 {u32 status; ≠5}`, optional `2030 {str}`, `2021 {u32}`.

**getservertime** ✔ `5000 {7-byte BCD: CC YY MM DD hh mm ss, JST}`.

**getinfo** ✔ `3000 {u32 n}` then n × `3010 {} 3030 {title} 3040 {body} 3020 {}`. No wrapping.
The game builds the Information screen itself (parser `0x527554`): `"
"`, then per item
3 × U+3000 + title, `"

"`, the body with 5 × U+3000 at the start of every line, and `"



"`
between items. The original service's titles started with "■ " (seen in a video of the Japanese
version); the server adds it via `format.news_title_marker`.

**getsignboardlist / getsignboarddetail** ✔ (empty) `4100 {0}` / `4160 {0} 41e5 {0} 41c5 {}`.

**getboardlist** ✔ (Daily tournaments shown in the menu)
```
4100 {u32 n} 4110 {u32 n}
n × [ 4120 {}  4140 {"Board_<index>"}  4150 {"Daily_YYYYMMDD_NN"}  4151 {""}  4152 {}
      4176 {u32 regulation id}  4177 {BCD yyyy mm dd start}  4178 {BCD end}  41a4 {""}  4130 {} ]
```
* `index` is 1…420. The client caches the first name it sees per index (`AddBoard 0x2dec8`, list at
  `global+0x4058`, 0x4c bytes each), so every day/slot needs its own index. The server uses
  `(days since 2026-01-01 + 140·(slot−1)) % 420 + 1`.
* There must be a board whose end date is after today (check `0x2e274`).
* Only **one** board is the Daily tournament: AddBoard stores a single current-board index
  (`+0x3ff8`) for a board whose date range covers today. With two boards for the same day, only
  one was offered (the client only requested `_01` lists), so the server sends one board per day.

**Regulation id** ✔ (u32, decoded by `0x536514` as `Daily_%04d%02d%02d_%02d`):
```
bits 28-31 year-2011 | 24-27 month | 19-23 day | bit 4 = 1 (Daily flag) | 0-3 slot (1..3)
example 2026-10-13 slot 1 = 0xfa680011 (4201119761)
```
* Bit 4 **must** be set. The client ORs it into the ids of its saved results (`0x532c1c`), and the
  entry screen compares those ids with this one to show "already joined" (which blocks re-entry).
* Slot 0 results never upload (the deferred upload walks slots 1–3 only), and id 0 is refused.

**getregulationdata** ✔ `6000 {UTF-8 text (BOM optional) + NUL}`: one line per board (max 3),
tab-separated, parsed by `0x52afd8` into 0x68-byte structs:
```
f0  id (u32)               -> +0x40
f1  name (we send the id)  -> +0x00
f2-5   4 bytes             +0x44..0x47  ? (no visible effect)
f6     u32                 +0x48        ?
f7-8   2 bytes             +0x4c        ?
f9     u16                 +0x4e        ?
f10-15 6 bytes  +0x50..0x55: 0x50-0x53 ? (sent 0,1,1,1) | 0x54 course | 0x55 holes mode
f16-31 16 bytes +0x56..0x65: 0x56 tee | 0x57 ? (round arg+1) | 0x58-5b ? | 0x5c,0x5d special rules |
                              0x5e,0x5f extra rules | 0x60 character | 0x61 club | 0x62 ball | 0x63-65 ? (1,1,1)
f32-33 ignored
```
* **course** (`+0x54`): 1 Maple Leaf, 2 Kagurayama, 3 Harvest Hills, 4 La Provence, 5 Al Arabiän,
  6 Legacy of Golf Links, 7 Mt. Sakura, 8 Mar Cielo, 9 Northern Fox. **0 = Practice Course crashes
  the round** (`0x3df98`). The value must be < 0x15. The player must own the course (`0x545b64`).
* **holes** (`+0x55`): see the field table below (1 = random 9, 2 = front 9, 3 = back 9, 4/5 =
  random 6/3). The confirmation screen labels everything that isn't 18 as "9 HOLES".
* **tee** (`+0x56`): 0 regular, 1 "Long Tee (Mirror)".
* **rules** `+0x5c..0x5f`: ids into the rule table (`Rule_Rule.txt`, §4.3); 0 = None. The entry is
  **Official** only if both `+0x5c` and `+0x5d` refer to rules whose `Official` column is 0
  (flag `+0x12a`, `0x4fb3fc`). Invalid non-zero ids crash the Tournament Entry screen.
* **restrictions**: `+0x60` character (0xff = any, else rule `0x57+v`), `+0x61` club (rule
  `0x17+v`), `+0x62` ball (rule `0x34+v`). Names: `server/data/gamedata.json`.
* Example line (Maple Leaf, 18 holes, regular tee, no rules, no restrictions):
  `4201119761\t4201119761\t0\t0\t0\t0\t0\t0\t0\t0\t0\t1\t1\t1\t1\t0\t0\t0\t0\t0\t0\t0\t0\t0\t0\t0\t255\t255\t255\t1\t1\t1\t0\t0\n`

**Regulation fields traced in code** (round setup `0x4e0578` → `0x69c448`, copies kept at
`global+0x10b28` and `(+0x880)+0x20e4` by `0x541474`):

| bytes | meaning (evidence) | Daily value |
|---|---|---|
| 0x44 | "tour" event flag. If 0x44 or 0x59 ≠ 0, the regulation's display name gets the suffix `" tour"` (`0x543e00`→`0x543d70`, string `0xc77428`). | 0 |

It seeds the round RNG (`+0x3c0`) and the hole-order shuffle (`0x69bbe0`), so everyone playing the board gets the same random holes. "No reader found" means no load of that byte from either regulation copy was found in the EBOOT,
so those bytes are probably unused padding or reserved fields.

**regscore** ✔ reply `4270 {u32 0} 42a0 {}`. Requests:
* `4140 "Daily_YYYYMMDD_NN"`, `42b0 "Name#@<tick or ISO time>"`, `ad8c {blob}` (deferred, type 7).
  The blob has an 8-byte header, then TLV: `4501 {i32 points, …}`, `38b4 {u32 hash + 0x46nn stat
  strings + 0x47nn per-hole score vs par (nn 0..17)}`, `8010`. Score = sum of the 0x47nn values.
* `4140 "Daily_…"`, `4500 {i64 score vs par}`, `4501 {u64 points}`, `38b4 {…}` (direct, type 11).
* `4140 "PointRanking"`, `4500 {8 bytes: u32 cumulative shot points, u32}`, `38b4 {stats}`.
* `4140 "KpiData"`, `4850 {u32 len}`, `4800 {telemetry}` (ignored).
* One Daily result per player per board. Later uploads are ignored; a direct upload's missing hole
  detail is filled in from the deferred one.

**getscorelist**: request `4140 {list name}`, `4000 {u32 first rank}`, `4010 {u32 count}`,
optional `4910 {comma-separated friend names}` for friend rankings. Replies by list name:

| list | reply |
|---|---|
| `Daily_…_score` ✔ | `4200 {n} 4210 {n} 4220 {0}` + n × `4250 {} 4270 {} 4500 {i16 score} 4501 {u16 0} 4502 {u32 players with that score} 4260 {}` (histogram; the game derives Player Count, Average and Temp. Rank) |
| `Daily_…_holescore` ? | sent empty (`4200 {0}…`); entries are u32 + 7 × u64 |
| `PlayerRanking_NNN`, count 1 ✔ | `4200 {1} 4210 {total} 4220 {1} 4230 {} 4270 {rank} 4500 {u32 TP, u32 TP}` (hi u32 → `global+0xb86b0`, shown as TP); no entry: `4200 {0} 4210 {total} 4220 {0}` |
| `PointRanking`, count 1 ✔ | `4200 {1} 4210 {total} 4220 {1} 4230 {} 4270 {rank} 4500 {8 bytes as uploaded}` + **consecutive** `0x4600, 0x4601, …` stat strings (field 0x13 is parsed as a number) |
| any list, count > 1 ✔ | **list format** (parser 0x527fcc): `4200 {n} 4210 {total} 4220 {has own row}` [own row: `4230 {} 4270 {rank} 4500 {…} 0x4600.. (≥15 strings) 4240 {}`] + n × `4250 {} 4270 {rank} 4500 {8 bytes} 0x4600.. 0020 {name, ≥12 bytes} 4260 {}` |
| `Daily_YYYYMMDD_NN`, count 1 ✔ | final result (parser 0x53c340): `4200 {1} 4210 {players} 4220 {1} 4230 {} 4270 {rank} 4500 {i32 score, u32 points} 4501 {u32 points, u32 0}` + `0x4600..0x461b` strings; `0x4614` = TP earned (Career/Best TP); 0x460f-0x4613, 0x4615, 0x461b are stored but unknown |

**getfinishboardlist** ✔ (Tournament History)
`6540 {} 6560 {u32 nA} 6580 {list A} 6550 {} 6570 {u32 nB} 6590 {list B}`. Lists are
concatenated 17-character names `Daily_YYYYMMDD_NN` + NUL (`0x525ae8`). List A entries are skipped
when the client already has a result record for the board; list B is always taken. The client then
fetches each board's final result (type 21). Only boards whose end time has passed should be
listed: while a board is still current, the client shows "Not participating".

**Tours / TP** ✔: TP (Tour Points) = sum of Daily points over the current tour. The server defines
tours as configurable date ranges ("series"), defaulting to the calendar month. The tour ranking
requests `PlayerRanking_<NNN>`, where NNN is a board index. The server ignores the number.

When no series covers a date, the tour is the **whole** calendar month (`settings.series_for`).
So after a series ends with nothing configured next, the fallback month also counts the Daily
results from the days of the finished series: points carry over instead of restarting at 0
(e.g. series Oct 10-20 then nothing: from Oct 21 the "October Tour" sums Oct 1-31). Configure the
next series before the current one ends to avoid this. The game's reaction to a mid-month tour
change is untested.

### 2.6 Daily result records in the save **(client side, for debugging)**

`global = *(0x17b8ef4)`. Record = `global + 0xbb9a4 + slot*0xcc + day*0x264 + month*0x4a1c`:
`+0xc` id, `+0x40` status (1 pending upload, 2 uploaded, 4 finished), `+0x44` score, `+0x48`
points, `+0x4c` rank, `+0x50` players, `+0x54` TP. Recent ids: `global+0xb86bc..0xb86c8`.

## 3. "Real" API (`/hsg6ps3/real/mg5_*.cgi`) ✔

A shared SCEJ "mg5" library inside the EBOOT.

* **Request:** POST body `param=` + URL-encoded `encrypt(b"version0=…,version1=…")`.
* **Response:** `encrypt(BE u32 checksum | "I5gM" | payload)`, where
  `checksum = (sum of all bytes with the checksum field zeroed) ^ 0x3566476d` (`0x916e88`).
* **Cipher** (`0x9f412c`): `K` = 32 bytes at `0xc2a568`
  (`427664969c805d58579c198e054a260df5487fd40c663473886682b1b6373843`); `prev` starts at 0.
  ```
  encrypt: c[i] = ((p[i] + prev) & 0xff) ^ K[i % 32];  prev = p[i]
  decrypt: p[i] = ((c[i] ^ K[i % 32]) - prev) & 0xff;  prev = p[i]
  example: encrypt("version0=0") = 34adb373405880c63af1
  ```
* Payload fields are big-endian.

| endpoint | payload (offsets include the 8-byte checksum/magic) |
|---|---|
| `mg5_get_event_data` | `+8 u32 status (0 OK, else shown as T-%06X)`, `+0xc u32 n entries`, `+0x10 u32 m base URLs`, 3 × u32 0, then n × 0x450-byte entries (`+0x04 size`, `+0x50 file name`), then m × 0x200-byte base URLs. Each file is fetched as `GET <base>/<name>`. We send n = 0. |
| `mg5_get_app_data` | same layout; one entry `appdata.xb` (§4) |
| `mg5_get_server_time` | `+8 u32 0, +0xc u32 0, +0x10 u64 unix seconds (UTC)`, then 16 zero bytes. Example plaintext: `35664430 4935674d 00000000 00000000 00000000 6acd7480 …` |
| `mg5_*_event_subscriber_count*` | 0x40 zero bytes |

## 4. App data archive (`appdata.xb`) ✔

### 4.1 FB archive format (chlib `MountBuffer` `0x778374`, lookup `0x779228`)

```
"FB\0\0" | u32 count | u32 names_size (>= 4, 4-aligned) | names (game ships 4 zero bytes)
count × 20-byte entries, sorted by hash: u32 hash | u32 name_off | u32 block_index | u32 stored | u32 raw (0 = not compressed)
data blocks in ENTRY order, each padded to 4; zlib-compressed when raw != 0
entry's data = block[block_index]
hash = Java String.hashCode of the lowercased path (h = h*31 + c, u32)
example: hash("lobby.csv") = 0x859e6bee
```
`server/fbarc.py` packs archives (index = position). `tools/extract_*.py` read the game's own
archives.

The game loads appdata in `0x53e880`. It succeeds only if the required files below are present and
non-empty; otherwise it shows `T-000000`.

### 4.3 `Rule_Rule.txt` ✔

UTF-8 with BOM, tab-separated, 221 rows: `Label No Official Challenge Online Adhoc …`. The full table is
inside `xbdata/chara_localize/chara_param.xb`; the entry named `data/param/chara/Rule_Rule.txt`
there is a 2-line stub. When online, the game reloads the rule table (`*(0x17b8ee0)`, 0x4c-byte
entries, loader `0x241d8`) from appdata. If the file is missing, the count stays 220 but the
array is NULL, and rounds crash. Rule names are in `message_text.US_01.xb` (table with "Real Golf Mode").

### 4.4 TO1 text tables ✔

```
"TO1\0" | u32 hash | u32 n | n × (u32 maxlen, u32 offset_of_string_offsets, u32 count) | strings (UTF-8, NUL)
```
The easy-chat file is the TO1 table from `xbdata/menu/message_text.US_0x.xb` whose sub-table counts
start `1,3,3,1,3,2,1`: sub-tables 0–6 = category names (Greetings; Congratulations ×3; Scores ×3;
Winning and Losing; Other ×3; Exclamations ×2; Comment History), 7–12 = phrases, 13–14 = room
messages. (The "ChatText" table that *looks* right — "I've started Hot Shots Golf…" — is the wrong one.)

### 4.5 `OnlineData_CommentList_US.txt` ✔ (parser `0x5c8e30`)

Tab-separated with a header row. Per row: label `Comment<L>_<NNN>`. Category = `L − 'A'`, except 'G',
which maps to 7 (category 6 is the comment history, fixed at 20 slots). NNN = phrase index. Columns
4–11 are bytes (flags; we send 1); column 12 is an int (we send 0). The menu pages each category in
pages of 20 and labels them with the category names. Up to 10 categories (`0x5cc244`). The flag
meanings and the original phrase→category assignment are **?**; the generated list uses phrase
table 7+k for category k.

### 4.6 Lobby layout CSVs ✔ (parsed in `0x53e880`; ',' separated, '\n' lines, **no header**)

```
club_house.csv   <n>,<name>                          (1..2 rows)
floor.csv        <n>,<name>,<variant>,<int>          n restarts at 1 for the next clubhouse (max 10 per club)
lobby.csv        <n>,<map>,<name>,<flag>,<capacity>  one block per CLUBHOUSE (shared by its floors), max 20
```
* Only **2 clubhouses** fit. The map table at `+0xcd4` is `[2][20]` u32, and a third group's names
  (`+0x52c + group*0x3d4`) overwrite it, so the game then loads garbage maps such as `lobby98`.
* `map` selects `xbdata/lobby/lobby%02d.xb`; the game ships maps **08–13**.
  `<variant>`/`<flag>` choose `lobby%02d%02d` sub-variants (0801–0803, 1001–1003, 1101–1103 exist).
* The game appends "Clubhouse"/"Floor" to the names. Thumbnails are fixed in
  `xbdata/menu/online_menu/choose_lobby/choose_lobby.US_01.xb`: `clb_000-002` (lion, flowers,
  golf flag), `flr_000-023` (floor image = club×10 + floor: 10 animals, 10 flowers, 4 golfers),
  `lby_000-006` (maps 08–14). The original (Vita) layout was clubhouse "Animal(s)" with floors
  Cat/Tiger/Elephant/….

## 5. Medius (lobby) ✔

* SCE-RT 3.02 (`rt_msg_client ReleaseVersion 3.02.200801141700`), Medius Client Library 3.02.
  Application id **24224**. The client sends `RT_MSG_CLIENT_HELLO` version **113** (PS3), **unencrypted**:
  it never sends `CRYPTKEY_PUBLIC`.
* Embedded SCERT certificate: 512-bit RSA, e = 17, modulus `d70c2d40…2483` (not factored). Not
  needed, since the client accepts an unencrypted server.
* **Flow:** MUIS `GetUniverseInformation` → MAS (session begin, localization, policy, DNAS
  signature, `AccountLogin` with name = password = online id) → MLS (`UpdateUserState`,
  announcements, `AccountUpdateStats`, `GetTotalUsers` 0xA1, `GameList` 0x29) → enter lobby:
  `GameList_ExtraInfo` → `CreateGame` (name `%02d%02d%02dU%02d` = clubhouse, floor, lobby (0-based),
  map; MaxPlayers 30) → `JoinGame` → DME `CONNECT_TCP_AUX_UDP` handshake → UDP via NAT. Leaving
  sends `EndGameReport` / `JoinChannel`. Multiplayer rooms are further games. Chat lines go through
  `TextFilter1` (lobby-ext 0x75/0x76) before broadcast.
* **Decoder strictness:** the library registers every message in `0x98da18` via
  `0x96df0c(id, class, encodeFn, 1, decodeFn)`. Decoders read fields **unaligned** with explicit
  skips (`0x96d738` int, `0x96d3e4` bytes, `0x96db04` skip). Any extra or missing padding
  misaligns the whole message, and the game drops the connection (disconnect reason 4). To check a
  reply, decompile its `decodeFn`. Two found so far:
  * `JoinGameResponse` (0x24, decoder `0xa20040`): msgid[21], skip 3, status, host type,
    NetConnectionInfo. **No** 4-byte trailer.
  * `TextFilterResponse1` (0x76, decoder `0xa16e2c`): msgid[21], status, int length,
    text[length]. **No** padding after the msgid. The game callback (`0x8028e4`) accepts the reply when
    status = 0 and shows the returned text.
* Game-side state for debugging: net object `*(*(0xd956e4))`, state at `+0x280`, join status `+0x804`;
  lobby manager `0x554d9c` (state `+8`); NetConnect `0x7fe494` → library `0x95834c`; event listener
  `0x5532d4`.
* **Friends List** uses `sceNpFriendlist` (RPCS3 limitation, see CHANGES.md §5). **Player Search** uses
  `MediusFindPlayer` by account name.
